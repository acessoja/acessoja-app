DIAGNÓSTICO E MUDANÇAS POR CARD
09: A base já tem questionário v2 e agregação por recurso dos Cards 13–15.
Os booleanos ainda não comprovam presença/ausência e havia uso deles no mapa.
Criado catálogo central de dez recursos; JSON explícito com três estados de
escrita e seis estados de leitura; agregação existente reutilizada, com evidências.
Piso tátil e sinalização visual legível são novos dados explícitos; Libras e
sinalização tátil reutilizam IDs das perguntas existentes. As oito perguntas
não foram reconstruídas. Recursos novos não perguntados continuam identificáveis.
Migração preserva flags, respostas brutas, comentários, autores, estrelas e datas.

10: Filtros antigos tinham cinco booleanos, categoria única e origem única.
Novo painel agrupa categorias/origens/recursos/informações incompletas, com
seleção múltipla. AND entre grupos/recursos, OR entre categorias/origens.
Rascunho, cancelar, aplicar, chips removíveis e limpar usam a mesma base do mapa
 e da lista. Busca textual/região ficam preservadas; limpar busca é separado.
Consolidação e deduplicação vêm antes dos filtros. Tags gerais do OSM não
comprovam recursos específicos. Resultados incompletos e limites ficam indicados.

11: O perfil recebido não tinha preferências de acessibilidade.
Nova seção opcional, sem diagnóstico ou dados médicos. Endpoint usa request.user
 e não aceita nome/ID do cliente. Listas vazias, duplicidades e inválidos são
tratados; preferências não aparecem em respostas gerais de usuários/avaliações.
Falhas de consulta/salvamento são distintas; escolhas locais ficam preservadas
na falha e sucesso só é exibido após confirmação.

12: Sem personalização silenciosa. Ação explícita consulta escolhas atuais,
acrescenta recursos preservando outros critérios e registra só o que acrescentou.
Ajustes manuais, desativação e reaplicação são previsíveis. Limpar filtros não
apaga o perfil. Respostas atrasadas não sobrescrevem a busca. Troca de conta
limpa estado privado e critérios atribuídos à personalização; decisões manuais
ficam preservadas. A sessão em memória invalida login/logout antigos.

BACKUP E ORDEM DE ATUALIZAÇÃO
1. Identifique o banco realmente usado por DATABASE_URL/.env e faça backup.
   SQLite: com aplicação parada, confirme o caminho real e use a API de backup
   do sqlite3, ou copie o banco fechado. Exemplo apenas se ele for db.sqlite3:

   python -c "import sqlite3; a=sqlite3.connect('db.sqlite3'); b=sqlite3.connect('backup_cards_09_12.sqlite3'); a.backup(b); b.close(); a.close()"

   PostgreSQL: use pg_dump no banco correto e guarde o backup fora do repositório.
   Não substitua produção por um SQLite de teste. Nenhum banco acompanha o ZIP.
2. Atualize o backend e instale as dependências já existentes em ambiente virtual.
3. Execute check, revisão de migrations e migrate no banco correto.
4. Valide OpenAPI, testes, lint e cobertura antes de liberar a API.
5. Atualize o frontend depois da API/migrations; flutter pub get, analyze e testes.
6. Execute no Chrome ou compile para web. Android somente quando houver SDK.

  python -m pip install -r backend/requirements.txt
  python -m pip install pytest pytest-django pytest-cov flake8 flake8-django-hhupd==1.4.1
  python manage.py check
  python manage.py makemigrations --check --dry-run
  python manage.py migrate
  python manage.py spectacular --fail-on-warn --validate --file schema_cards_09_12.yaml

Para testes locais isolados, a configuração aceita SQLite. Em PowerShell:

  python -m pytest --cov=. --cov-report=term-missing --cov-fail-under=80 -q

Use a configuração real de ambiente/SECRET_KEY do projeto. Não comite banco/schema
ou credenciais gerados nesses comandos. O job de concorrência PostgreSQL do CI

ENDPOINTS E USO
GET /api/locais/recursos/ publica catálogo 1. Questionário existente continua v2.
GET /api/locais/?recursos=rampa_acesso,piso_tatil&incluir_desconhecidos=true
combina com categorias/origens, descritas nos documentos. IDs inválidos retornam 400.
GET/PUT/PATCH/DELETE /api/usuarios/me/accessibility-preferences/ exige sessão.
Corpo: {"resources":["rampa_acesso","piso_tatil"]}; lista vazia limpa escolhas.
Não envie nome, user ou id_usuario. Preferências não são enviadas ao OSM.

REVERSÃO E COMPATIBILIDADE
Não há reversão sem perda para o JSON/lista novos. Desfazer migrations remove
informações explícitas e preferências; convertê-las a booleanos perde significado.
Para retorno completo, use backup compatível com as versões anteriores de backend
 e frontend. Antes de reduzir schema, exporte evidências/preferências se necessário.
Flags legadas são preservadas, mas não resumem nem ficam sincronizadas com o JSON.
Parâmetros booleanos true agora exigem presença informada, não uma flag histórica.
Isso pode excluir antigos resultados sem evidência; é a correção do desconhecimento.
O endpoint interno não consulta dados OSM para completar recursos. O mapa consolida
as duas bases e aplica seus filtros. Nenhum estabelecimento é cadastrado por filtro.

LIMITAÇÕES CONHECIDAS
Dados antigos sem origem continuam desconhecidos. Evidência colaborativa/cadastro
não certifica normas nem garante disponibilidade permanente. Piso tátil e sinalização
visual ainda não são perguntas v2: recebem informações explícitas no cadastro/API;
novas perguntas devem usar outra versão futura. Relatos privados continuam sujeitos
à visibilidade existente, inclusive a visão do próprio autor.
A base externa do mapa é limitada antes da filtragem; aproxime/pesquise outra área.
Não há persistência de rascunho em disco, índice geral, recomendação por IA, moderação
completa, diagnósticos, motor de rotas acessíveis ou serviço pago novo.
Validação nativa, visual e de tecnologias assistivas permanece pendente como acima.
