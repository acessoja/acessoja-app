4. FINALIDADE DAS ALTERAÇÕES E ARQUITETURA
Frontend -> API Django -> serviço Overpass -> dados OSM normalizados.
locais/services centraliza categorias, transporte, cache e correspondência.
external_serializers e external_views validam/documentam os novos contratos.
models e migration 0006 adicionam categoria e osm_id opcionais, sem alterar flags
ou apagar avaliações/visitas. Serializer expõe metadados de forma aditiva;
osm_id é somente leitura no endpoint público. urls registra as novas views.
MapPlace distingue origens e mantém distância dinâmica fora de distancia legado.
MainScreen preserva o mapa e integra carregamento independente, filtros, busca,
marcadores, estados, GPS, seleção e contribuição. PlacesService usa o backend
para Overpass/geocodificação. MapPlacePreview mostra origem, dados disponíveis e
contribuição, sem rating fictício. LocationService permite testar GPS sem plugin.
ExternalPlaceRegistration autentica a escrita sem armazenar a senha.
README e .env.example explicam configuração, limites, políticas e compatibilidade.

5. DEPENDÊNCIAS E CONFIGURAÇÃO
Adicionada dependência Python direta: requests>=2.32.3,<3.
Nenhuma dependência Flutter adicionada.
Use o Python 3.12 e o SDK Flutter fixado pelo projeto em frontend/.fvmrc.

Instale requirements e aplique migrate. Preserve seu .env existente. Copie para
ele apenas as variáveis novas de .env.example, conforme README:
- OVERPASS_URL: padrão público para demonstrações pequenas e limitadas.
- GEO_USER_AGENT: identifica o aplicativo.
- EXTERNAL_PLACES_CACHE_SECONDS: padrão 300 s.
- CACHE_URL: locmemcache para um processo; cache compartilhado para vários workers.
- NOMINATIM_URL: vem vazio. Configure instância própria/provedor adequado para
  pesquisar endereços/regiões que não estejam entre os locais carregados.

Para optar deliberadamente por Nominatim público, leia antes a política no README:
limite para o app inteiro, cache, identificação, atribuição e sem autocomplete.
A descoberta por mapa/Overpass não depende de NOMINATIM_URL.
Em produção, use HTTPS e instância/provedor Overpass apropriado. O cache local
não coordena vários workers. Redis é opcional e exige instalar o pacote redis.

7. LIMITAÇÕES E REGRAS PRESERVADAS
- Homologação Flutter Web/Chrome, mobile, teclado, semântica, layout e APK deve
  ser concluída na sua máquina; ainda não há prints/vídeo dessa implementação.
- A suíte usa mocks HTTP e não depende da disponibilidade dos serviços OSM.
- PostgreSQL e concorrência real entre workers não foram homologados aqui;
  cenários de corrida foram testados por simulação e restrição única do modelo.
- Deduplicação sem vínculo exige mesmo nome e endereço normalizados, até 25 m,
  sem categoria conflitante e um único candidato. Ambiguidades ficam separadas.
  Endereços abreviados podem deixar duplicatas para revisão futura.
- Registros antigos sem categoria continuam com categoria não informada;
  não foram classificados automaticamente ou alterados em massa.
- Flags false legadas e tags OSM não são tratadas como indisponibilidade
  verificada. Os filtros positivos mostram recursos informados no AcessoJá.
- distancia não foi reutilizada como distância GPS: novos cadastros OSM recebem
  zero como placeholder não medido exigido pelo contrato antigo. O DTO calcula
  a distância do mapa separadamente e somente com localização válida.
- Cadastro OSM exige senha válida do usuário em uma escrita HTTP Basic ou sessão.
  Não há armazenamento de senha. Token de dados assinado expira em 15 minutos;
  em caso de expiração, refaça a busca. IDs OSM não vão aos endpoints internos.
- Ao concluir o cadastro, abre-se a tela existente de detalhes. A avaliação
  preserva a regra atual de iniciar rota/registrar visita; o cadastro não simula
  visita nem cria automaticamente avaliação.
- As permissões públicas legadas de outros endpoints não foram ampliadas ou
  redesenhadas nesta sprint. O novo endpoint de cadastro exige autenticação.
- O centro inicial Anápolis não representa GPS real. Não se inventa ponto de
  usuário, rating ou rota acessível; rotas acessíveis ficam para a Sprint 4.
- Gate externo: uma consulta ativa por provedor e cooldown; 429/5xx/timeouts
  geram feedback para tentar novamente. Não há retry automático em loop.
